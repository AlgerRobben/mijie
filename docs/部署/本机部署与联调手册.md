## 一、Canal与RocketMQ缓存同步部署

本机部署已于 2026-10-07 完成：MySQL 9.6.0、Canal 1.1.8、现有 RocketMQ 5.3.3、项目客户端 4.9.8、JDK 21 和 OpenResty 1.27.1.2。服务以 Windows 隐藏进程运行，不依赖 Docker。

```mermaid
flowchart LR
  DB[MySQL商铺及缓存版本表] -->|ROW/FULL Binlog| Canal
  Canal -->|flat JSON| MQ[RocketMQ hmdp-shop-change]
  MQ --> Consumer[集群消费者 回查当前事实]
  Consumer -->|NORMAL失效 HOT立即重建| Redis
  Redis -->|源发布Pub/Sub| Local[在线JVM保留HOT旧值并刷新]
  Consumer -->|认证HTTP通知| Edge[边缘保留HOT旧值并刷新]
```

### 当前行为（2026-10-13固定分类与普通旧值异步刷新）

- 处理`hmdp.tb_shop`与`hmdp.tb_shop_cache_version`的INSERT/UPDATE/DELETE；版本事件取shop_id，直接SQL由V4触发器提升版本。
- 普通商铺只缓存Redis，物理TTL30分钟，不存在占位2分钟；fresh=false下已有正文仅信息版本落后时先响应旧值、后台刷新源，不续旧TTL、不存上层。已知删除/重新插入导致存在状态相反仍严格恢复；热点三层均无物理TTL，Redis源逻辑30分钟，Caffeine/边缘逻辑5秒，过期先返回旧值并异步刷新。
- 删除的HOT固定名单保留该ID，版本表保留删除记录，有效路由转NORMAL并清理HOT正文；不存在占位物理2分钟，避免丢失重建通知后永久返回不存在。
- 热点身份由固定配置名单确定，数据版本持久化；源发布Lua检查RLock owner、已观察版本和模式；NORMAL更新失效源，HOT更新立即申请源重建。消息回查当前主库，迟到消息不发布旧payload。
- 固定HOT名单的源发布或删除通过`hmdp:cache:shop:v3:<库号>`通知在线JVM；普通非热点商铺不广播，因为Caffeine中没有其副本。Pub/Sub未送达可由本地5秒逻辑检查在后续查询时恢复，没有定期扫描/重连对账；Redis源本身未更新时不能宣称5秒收敛。
- MQ路径失败返回RECONSUME_LATER，默认重试8次后Broker DLQ。边缘HTTP200是后台刷新已注册，后台刷新失败仍保留旧值，后续查询再试。
- 事务提交后观察版本并提交有界后台任务，异常记录SHOP_CACHE_INVALIDATION_FAILED；已提交数据库事务不因缓存异常回滚，CDC独立恢复。

Canal的官方deployer安装包解压到 `.local/canal-1.1.8`，由 `start-canal.ps1` 使用JDK 21运行 `com.alibaba.otter.canal.deployer.CanalLauncher`。它是独立的Windows Java进程，与运行业务JAR的Java进程分开。当前使用 `rocketMQ` 模式：从本机MySQL读取Binlog，将商铺与数据版本变更发送到MQ，再由业务实例按固定名单分类失效或刷新缓存。

**两个端口的用途：**

- **18110管理端口**：Canal Server提供给管理客户端的协议端口，可用于查询状态、管理实例等。它不是浏览器管理页面；可视化的Canal Admin需要另行部署，当前脚本未部署该Web应用。此端口也不是MySQL账号登录端口。
- **18112指标端口**：通过HTTP向Prometheus等监控工具提供采集事务数、Binlog字节数、采集延迟等指标。指标反映Canal运行情况；当前脚本未部署Prometheus/Grafana看板。

**“保存的账号”和“采集位点”是两类独立信息：**

| 信息 / 文件（相对工程根目录）              | 含义                                                                     |
| ------------------------------------------ | ------------------------------------------------------------------------ |
| `.local/cache-sync/canal-account.json`     | Canal连接MySQL的专用账号与密码；脚本复用该文件，不在每次启动时生成新密码 |
| `.local/canal-1.1.8/conf/example/meta.dat` | 已记录的Binlog进度，例如日志文件名和文件内偏移量；重启时用于续读         |
| `.local/canal-1.1.8/conf/example/h2.mv.db` | TSDB保存的表结构历史，帮助按变更发生时的结构解析Binlog                   |

账号解决“是否有权读取”，位点解决“从哪里继续读取”。例如 `binlog.000061` 的某个字节偏移是日志中的位置，不是商铺ID、表的行号，也不属于某个登录账号。重启恢复可能重新投递已处理的事件，因此缓存失效消费者允许重复处理。

专用MySQL账号 `hmdp_canal_local` 仅允许从本机登录，只有SELECT和复制权限；Canal TSDB初始化需要跨库读取表元数据，Binlog采集过滤器仍限定商铺和缓存版本表。凭据保存在被忽略的 `.local` 中。服务PID、标准日志和MQ存储位于 `.local/cache-sync`；保留采集位点、TSDB及MQ存储，才能保留已有采集与消费进度。

| 可分享的关键配置模板                       | 实际配置（相对工程根目录）                            | 控制内容                                        |
| ------------------------------------------ | ----------------------------------------------------- | ----------------------------------------------- |
| `deploy/canal/canal.properties.example`    | `.local/canal-1.1.8/conf/canal.properties`            | Server运行模式、管理/指标端口、MQ地址和发送参数 |
| `deploy/canal/instance.properties.example` | `.local/canal-1.1.8/conf/example/instance.properties` | MySQL地址、复制账号、采集表过滤器和投递主题     |

### 启动与停止

在项目根目录的 PowerShell 中运行：

```powershell
# 仅首次下载或重建本机环境时需要；官方安装包来源见文末。
New-Item -ItemType Directory -Force .local/canal-1.1.8 | Out-Null
New-Item -ItemType Directory -Force .local/downloads | Out-Null
curl.exe --ssl-revoke-best-effort --fail --location https://github.com/alibaba/canal/releases/download/canal-1.1.8/canal.deployer-1.1.8.tar.gz --output .local/downloads/canal.deployer-1.1.8.tar.gz
tar -xzf .local/downloads/canal.deployer-1.1.8.tar.gz -C .local/canal-1.1.8

# 打包前先停止占用 JAR 的应用。
./deploy/canal/stop-local.ps1 -Services @('app-8081','app-8082')
$env:JAVA_HOME='D:\JDK21\jdk-21.0.12.1+1'
$env:PATH="$env:JAVA_HOME\bin;$env:PATH"
mvn -DskipTests package
./deploy/canal/start-local.ps1

# 停止脚本只操作 PID 文件对应且启动命令与项目服务匹配的进程。
./deploy/canal/stop-local.ps1
```

MySQL与Redis虚拟机先启动，Java就绪后启动OpenResty；OpenResty启动步骤见 [边缘缓存部署说明](本机部署与联调手册.md#二openresty边缘层部署)。脚本可通过 `-RocketMqHome` 和 `-JavaHome` 指定安装目录。`start-app.ps1` 默认启用商铺变更MQ消费、边缘通知和订单Stream消费。订单消费者需要先部署订单任务表，见[业务设计中的订单恢复说明](../业务/核心业务设计与技术实现.md#order-recovery)。

IDEA 启动项目时可设置环境变量 `HMDP_CANAL_ENABLED=true`、`HMDP_EDGE_INVALIDATE_URLS=http://127.0.0.1:8080/internal/cache/shop`，并先停止脚本启动的 8081 实例以释放端口。项目默认配置仍允许不启用 MQ；`HMDP_ROCKETMQ_NAMESRV` 默认指向本机。

### 脚本调用关系与消费开关

所有脚本后缀均为 `.ps1`（数字1）。`start-mq.ps1` 只启动NameServer/Broker，`start-canal.ps1` 只启动Canal，`start-app.ps1` 只启动业务JAR。`start-local.ps1` 是把这些步骤组合起来的一键启动脚本，其调用顺序为：

```text
start-local.ps1
  1. start-mq.ps1    → 启动NameServer与Broker
  2. mq-admin.ps1    → 创建/更新hmdp-shop-change主题
  3. start-canal.ps1 → 启动独立Canal进程
  4. start-app.ps1   → 启动8081业务实例（默认打开两个消费者）
```

这里复用同一组脚本，没有复制各服务的启动实现。MQ或Canal已经启动时，可以单独使用 `start-app.ps1`；只需重启Canal时，可以单独使用 `start-canal.ps1`。

`start-app.ps1` 将参数转成Spring Boot命令行配置，开关作用范围是**本次启动的Java业务实例**：

| 脚本参数（默认均为`$true`） | Java配置                               | 作用                                                                                                                                                                 |
| --------------------------- | -------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `-ConsumeCanal`             | `hmdp.canal.enabled`                   | 决定是否创建商铺变更RocketMQ消费者；见[CanalRocketMqConfig](../../src/main/java/com/hmdp/config/CanalRocketMqConfig.java)的`@ConditionalOnProperty`                  |
| `-ConsumeOrders`            | `hmdp.seckill.stream-consumer.enabled` | 决定是否启动订单Stream消费线程及失败补偿扫描；见[VoucherOrderServiceImpl](../../src/main/java/com/hmdp/service/impl/VoucherOrderServiceImpl.java)的`startConsumer()` |

`-ConsumeCanal $false` 不会停止独立Canal进程，Canal仍可采集并向MQ发送消息。`-ConsumeOrders $false` 不会关闭秒杀下单HTTP接口；接口仍可受理并写入Stream，需要其他启用消费者的业务实例处理订单。

```powershell
# 在工程根目录执行：缓存联调实例消费商铺变更，不消费订单。
./deploy/canal/start-app.ps1 -Port 8082 -ConsumeCanal $true -ConsumeOrders $false

# 只停止8082业务实例，其他链路服务继续运行。
./deploy/canal/stop-local.ps1 -Services @('app-8082')

# 只停止Canal采集进程。
./deploy/canal/stop-local.ps1 -Services @('canal')
```

这些开关在启动时读取；对已经运行的实例再次执行启动脚本会直接返回，不会在线修改开关，需要先停止对应实例再以新参数启动。IDEA直接启动时，`application.yaml` 的商铺变更MQ消费默认关闭，可以通过上述环境变量启用；订单消费默认开启。

**停止时的PID校验：** PID是操作系统分配的进程编号，启动脚本把它写入 `.local/cache-sync/<服务名>.pid`。停止脚本先读取所选服务的PID，再查询该进程的完整启动命令，核对RocketMQ启动类、Canal目录或本项目JAR路径，避免旧PID被其他程序复用后误停无关进程。对业务实例核对JAR路径和启动端口。校验通过后执行 `taskkill /PID ... /F`，属于强制结束，不是等待业务请求完成的优雅停机。

`stop-local.ps1` 不传参数时依次处理 `app-8082`、`app-8081`、`canal`、`broker`、`namesrv`；传 `-Services` 时只处理列出的服务。它不会停止MySQL、Redis虚拟机或OpenResty。

### 迁移、维护与复测

当前已有库已执行V4：把V3的版本和删除记录复制到`tb_shop_cache_version`，替换触发器并删除`tb_shop_cache_policy`。冷热名单不再存数据库，源逻辑期限统一配置。新库`hmdp.sql`直接包含当前版本表/触发器；不要用全量SQL覆盖已有业务数据。V1/V2仍用于订单约束与任务表，V3留作历史增量迁移，未执行过V3的老库需先执行V3，再执行V4。

迁移前停止占用JAR的旧应用和Canal并备份。`migrate-shop-cache.ps1`备份schema/触发器及旧策略数据，V4要求旧V3表仍存在，**已完成V4的本机无需重跑**。MySQL DDL不支持整套事务回滚，回退需使用备份结构/数据及配套旧代码。

```powershell
./deploy/canal/stop-local.ps1 -Services @('app-8081','app-8082','canal')
# 尚未升级到V4时才执行：
./deploy/canal/migrate-shop-cache.ps1
# start-canal使用商铺+版本表过滤器，保留账号及采集位点。
./deploy/canal/start-canal.ps1
```

固定HOT默认10号，其余商铺NORMAL。`application.yaml`的`hmdp.cache.hot.ids`、环境变量`HMDP_HOT_SHOP_IDS`，或`start-app.ps1 -HotShopIds '10,11'`在启动时决定名单。各实例必须一致；`-RedisDatabase`决定库号，`-CanalConsumerGroup`决定商铺消费组，日常分别默认0和hmdp-shop-cache。`-HotLocalLogicalTtlSeconds`默认5；原LocalTtlSeconds别名保留，指逻辑期限。

同库源配置指纹保存在`cache:shop:v3:catalog`。在线改名单会破坏已有分类，当前不支持在线变更。维护时先停该库全部业务/边缘实例，仅清理项目`cache:shop:v3:*`及`lock:shop:rebuild:v3:*`命名空间，再统一配置重启。不能FLUSHDB；同一Redis库中的登录、GEO、订单数据不属于商铺缓存清理范围。

复测步骤（会写同一MySQL中的两条专用商铺，Redis使用15号库）：

```powershell
./deploy/canal/stop-local.ps1 -Services @('app-8081','app-8082')
```

### 常驻容量

固定名单默认10号、上限500家、Caffeine最大1000条、边缘正文10MiB、协调1MiB；每个源快照/边缘编码条目上限8192字节，超限拒绝准入或发布。Caffeine不设置物理到期；shared_dict用safe_set且TTL=0，容量不足不能强制淘汰其他HOT。

2026-10-10的14条真实商铺字段JSON估计合计9017字节、最大724字节。这是JSON字段估计，不是Java对象保留内存。预算按Java每条峰值16KiB、边缘每条8KiB，再考虑两份替换余量：500家约16MiB Java和8MiB边缘；JVM热点预算32MiB/512MiB堆、边缘10MiB。边缘slab取整、元信息与字段增长仍需测量，不能把此预算当作已完成500家容量压测。当前验收记录实际编码大小、条目数和shared_dict freeSpace。

### 运维与边界

监控 `SHOP_CACHE_CDC_RETRY`、`SHOP_CACHE_INVALIDATION_FAILED`、消费者积压和 `%DLQ%hmdp-shop-cache`。可执行：

`mq-admin.ps1` 是调用MQ管理命令行的便捷脚本。“入口”指从该脚本发起命令，不表示网络端口或Web管理页面。`-Command` 选择子命令，`-MqArguments` 提供参数：`consumerProgress` 查询消费组的消费进度与积压，`topicStatus` 查询主题各队列的消息偏移，`updateTopic` 创建/修改主题。查询死信主题的偏移可辅助判断是否有死信；查看具体消息和人工重放是另一步操作。执行输出保存到 `.local/cache-sync/mq-admin-<命令>.log`。

```powershell
./deploy/canal/mq-admin.ps1 -Command consumerProgress -MqArguments @('-n','127.0.0.1:9876','-g','hmdp-shop-cache')
./deploy/canal/mq-admin.ps1 -Command topicStatus -MqArguments @('-n','127.0.0.1:9876','-t','%DLQ%hmdp-shop-cache')
```

DLQ 主题在首次出现死信后才存在。重放前核对原消息中的商铺 ID、修复失败端点，再将原始合法消息重新投递到业务主题；重复通知不会创建订单；固定分类下始终回查当前数据版本与业务事实。当前尚未接入外部告警平台，也未提供自动死信重放。

此部署是本机单 Broker 功能联调。未验证Broker高可用或生产容量；本轮验证了受控回填和旧版本拒绝。当前消费者只同步商铺详情缓存，不维护 GEO 索引；DDL/TRUNCATE 不属于此处的 DML 消息处理范围。CDC、重试与 TTL 提供最终一致性的恢复手段，普通物理TTL/HOT逻辑期限是有查询时的恢复兜底，依赖长期失败时HOT仍可返回旧值，不保证零延迟或严格一致性。

## 二、OpenResty边缘层部署

本地安装的是官方 `openresty-1.27.1.2-win64.zip`，位于项目 `.local/openresty-1.27.1.2-win64/`。原有 `D:/JavaCode/nginx-1.18.0-hmdp/nginx.exe` 不含 Lua 模块，仍可保留作对照。安装包来自 <https://openresty.org/download/openresty-1.27.1.2-win64.zip>；本次下载的 SHA-256 为 `A110CEBF633899FAA10D3DACC9EFFD1A98C5FB82E347EC1EA8092300320DF86B`。

保留的 ZIP 已归档到 `.local/downloads/openresty-1.27.1.2-win64.zip`。运行目录仍为上面的安装目录；配置源文件在 `deploy/openresty/`。

### 链路

HOT：`:8080/api/shop/{id}`先读常驻shared_dict，再读Redis有效HOT快照；真正缺失使用认证内部Java fresh接口，同ID合并/分布式锁回源并重建Redis。NORMAL：边缘不保存响应，Redis快照仅版本落后时先返回旧值并注册普通源timer；缺失或已知存在状态相反由Java互斥回源。直接Java查询可命中HOT Caffeine；边缘内部fresh请求不允许Caffeine短路源恢复。

响应头`X-HMDP-Cache=shared/redis/backend`表示本次边缘取数位置；`X-HMDP-Cache-Stale=true`表示边缘当次发现逻辑到期仍返回旧值。它不是整体一致性的证明。

### 启动与配置

1. 官方Windows OpenResty解压在`.local/openresty-1.27.1.2-win64`，静态前端在html/hmdp；源码配置在deploy/openresty，启动脚本同步配置/Lua并备份旧conf。
2. 先启动Java等待就绪，由Java生成/复用`.local/cache-sync/internal-cache-key.txt`；再运行`./deploy/openresty/start-openresty.ps1 -Restart`。脚本从当前yaml读取Redis连接、通过环境变量注入密码和内部密钥，不写入nginx.conf或Java命令行。
3. 默认Redis库0、Java8081、HOT局部逻辑5秒；诊断可用-RedisDatabase、-JavaPort、-HotLogicalTtlSeconds。完整重启才能继承新环境，单reload不能更新这些值。
4. nginx -t通过后隐藏启动，worker0一次预热全部有效HOT。只停止安装目录匹配的nginx进程；其他Nginx不受影响。

nginx.conf的events/worker_connections控制每worker连接容量，包含客户端和上游；10m是共享字典容量，条目的5秒期限放在JSON内部。HMDP_REDIS_DB是SELECT的逻辑库编号；Pub/Sub另靠频道名隔离。

维护/诊断接口要求本机来源和X-HMDP-Internal-Key密钥。Java `/internal/shop-cache`仅提供快照、固定有效HOT名单和stats；边缘 `/internal/cache/shop/{id}`提供刷新/退役通知、`/internal/cache/stats`供诊断。边缘显式拒绝`/api/internal/`代理，防远端伪装本机。远端部署需重新设计受信网络/认证配置，不能直接放开内部接口。

### 语义变化

HOT第一次边缘缺失可能redis命中，后续shared命中；局部逻辑到期后仍shared并后台刷新。更新时不再先清空HOT正文，也不保证首次一定backend。NORMAL和不存在结果永远不写边缘/Caffeine，因此不存在旧版“backend→redis→shared”负缓存流程。

本机使用Windows原生OpenResty；Docker Desktop和虚拟机内OpenResty未作为本次依赖。固定分类功能验收记录位于`.local/verification/fixed-cache/`，当前性能结果见[实测数据与分析](../测试/性能与可用性测试手册.md#实测数据)。

### 普通旧版本刷新（2026-10-13）

Java普通后台池和HOT副本池各默认4线程，共享默认4线程的源重建池，均不积压任务。普通按ID标记合并、获标记后检查源是否已更新；失败退避500ms，提交被拒绝退避100ms。Java的1024条协调Caffeine只保存退避期限、保留1秒，不存普通正文。边缘normal-flight标记租约5秒，刷新回调检查归属与源版本；使用fresh=true，结果不安装shared_dict。

部署仍使用原启动脚本；这次不需要SQL迁移、配置指纹或Redis命名空间更换。普通CDC失效和版本发布围栏保留。阅读详情见[内部回源接口与并发重建](../业务/核心业务设计与技术实现.md#internal-shop-cache)；定向验证的完整本机证据位于`.local/verification/normal-stale/`，归档入口见[数据与完整证据](../测试/性能与可用性测试手册.md#测试数据)。

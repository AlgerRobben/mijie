# 性能与可用性测试手册

适用版本：固定热点名单、热点无物理TTL、普通旧值异步刷新及订单失败补偿。

入口实例：接收商铺查询、秒杀申请等 HTTP 请求；关闭订单 Stream 消费和商铺变更 MQ 消费。

## 二、k6 压测工具介绍

k6 是 Grafana 提供的开源性能测试工具。通过 JavaScript 脚本定义请求、负载和校验规则，再用命令行运行，模拟大量用户访问接口，观察系统的响应速度、正确率与稳定性。[k6 官方介绍](https://grafana.com/docs/k6/latest/)

### k6 可以做什么

| 能力           | 本项目中的例子                                      |
| -------------- | --------------------------------------------------- |
| 批量发送请求   | 查询商铺、提交秒杀申请                              |
| 控制负载       | 每秒计划发起600次请求，持续30秒                     |
| 模拟并发       | 多个虚拟用户同时执行请求                            |
| 统计性能       | 实际RPS、p50/p95/p99、HTTP错误率、dropped           |
| 校验业务与验收 | 核对商铺ID、订单受理/拒绝结果，检查指标是否满足阈值 |

**VU（Virtual User，虚拟用户）**是执行脚本的模拟用户，**迭代**是执行一遍测试函数。本项目每次迭代发送一次HTTP请求，因此目标迭代率对应目标请求率；VU数量表示执行请求的并发资源，与每秒请求数是两个概念。

### 本项目如何使用 k6

本轮使用 k6 2.3.0，脚本为 [load-current.js](../../deploy/performance/load-current.js)，主要分为三个阶段：

1. **配置场景和负载。** 指定Java或OpenResty入口、商铺或秒杀接口、目标RPS与测试时长。稳态采用 `constant-arrival-rate`，按计划启动请求；预分配60个VU，最多扩展到120个。没有空闲VU时，未能启动的迭代计入dropped。
2. **发请求并校验响应。** 商铺查询检查HTTP状态、业务成功标记和返回的商铺ID，同时统计缓存命中来源；秒杀区分正常受理、库存不足/重复下单等预期拒绝及异常结果。
3. **输出指标并判断结果。** 汇总延迟、错误率、内容正确率及dropped，导出JSON供报告汇总。脚本阈值为HTTP错误率≤0.1%、内容正确率≥99.9%、异常业务结果为0、dropped为0；任一阈值未满足，k6会将测试判为未通过。[阈值机制](https://grafana.com/docs/k6/latest/using-k6/thresholds/)

### k6 与最终业务核对如何分工

k6 负责制造流量和测量接口表现。秒杀接口返回订单ID表示申请已受理，订单最终是否落库、库存是否正确、补偿是否完成，由配套Java工具查询MySQL和Redis核对；Python脚本负责部署、分轮执行、故障注入、资源采样及报告整理。

## 三、测试方案、原理与判定

### 场景矩阵

RPS，即Requests Per Second，表示每秒请求数，用于衡量请求流量或系统吞吐量。

响应时间指标p95，即约95%的已完成请求耗时不超过该值。

dropped总数指未能成功发起的请求数量。

| 场景                | 负载与重复                                                                    | 核对内容                                            |
| ------------------- | ----------------------------------------------------------------------------- | --------------------------------------------------- |
| HOT边缘/直连Java    | 100/300/600RPS，每轮30秒，各三轮                                              | p50/p95/p99、正确率、dropped和资源                  |
| NORMAL边缘/直连Java | 300RPS，各三轮30秒                                                            | 正文仅在Redis，不进入shared_dict/Caffeine           |
| 混合读              | 80%HOT、20%NORMAL，300RPS，三轮                                               | 正确性、延迟、实际吞吐                              |
| 秒杀持续受理        | 10/30/60RPS，各三轮30秒、每轮新券                                             | 接口与终态延迟分别测量，核对库存/唯一用户           |
| 库存/幂等           | 库存300、目标200RPS；同人请求约200次；成功消息重放100次                       | 不超卖、不重复建单/扣库存，PEL与未读消息都排空      |
| CDC                 | HOT/NORMAL空载及300RPS背景读，各30次SQL更新                                   | 四组120样本，三个入口新值及HTTP通知证据             |
| 故障                | MySQL断连、消费者退出、Redis断连、永久落库失败、Canal/Broker重启、边缘通知503 | 积压恢复、Pending接管、真实MQ重投、FAILED及幂等补偿 |

### 4.4 故障与一致性核对

| 故障                  | 关键数据与结果                                                                                               |
| --------------------- | ------------------------------------------------------------------------------------------------------------ |
| MySQL代理中断         | 51笔全部受理，恢复后全部落库；恢复后排空观察约3.92秒                                                         |
| 消费者退出/新实例接管 | 退出时1笔Pending、20笔未读；新实例启动约10.18秒，再约16.69秒排空，21单全部完成                               |
| Redis代理中断         | 401次热点边缘查询全部成功；恢复后核对正常                                                                    |
| 永久落库失败          | Redis库存10/MySQL0，5笔受理后约122.8～123.9秒均FAILED且补偿；订单0、Redis库存10、预占/购买记录0、DLQ0、归档5 |
| Canal停止10秒后重启   | 沿用账号/位点，重启开始至全入口新值约10.47秒；两次成功CDC边缘通知                                            |
| Broker停止10秒后重启  | 沿用存储，重启开始至全入口新值约21.52秒；两次成功CDC边缘通知                                                 |
| 边缘通知临时503       | 两次失败后恢复，两条消息均真实ACK retries=1，全入口新值                                                      |

故障范围为专用连接和登记进程，未演练断电、磁盘损坏、Redis/MySQL主从切换或多Broker高可用。
